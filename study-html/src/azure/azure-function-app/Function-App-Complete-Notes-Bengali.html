Q1
Azure Functions & Function App — Complete Fundamentals

Azure Functions কেন তৈরি হলো — সমস্যাটা কোথায় ছিল?

ধর তুমি একটা e-commerce application চালাচ্ছ। রাত ১১টায় প্রতিদিন sales report তৈরি করতে হয়। বাকি ২৩ ঘণ্টা কিছুই করার নেই। কিন্তু traditional Web API বা App Service-এ VM সারাক্ষণ চলতে থাকে — ২৪ ঘণ্টাই পয়সা যায় — এমনকি যখন কোনো কাজ নেই তখনও।

আবার ধর, কোনো user যখনই Blob Storage-এ image upload করে, সেটা process করতে হবে। দিনে ৫টা হতে পারে, আবার ৫০,০০০টাও হতে পারে। Traditional server-এ সবচেয়ে বেশি load-এর কথা ভেবে capacity রাখতে হয় — বেশিরভাগ সময় সেটা idle পড়ে থাকে।

Azure Functions ঠিক এই দুটো সমস্যা সমাধান করতে এসেছে: শুধু যখন code চলে তখনই পয়সা দাও, আর infrastructure নিজেই manage করুক।

Core Concept

Azure Functions হলো একটা serverless compute service। তুমি শুধু একটা ছোট্ট focused code লিখবে (সেটাই Function)। Azure নিজেই host, runtime, infrastructure, scaling, আর OS সব সামলাবে। তোমার code যখন actually execute হবে, শুধু তখনই bill আসবে।

Function vs Function App — এই দুটো গুলিয়ে ফেলো না

Interview-এ এটা সবচেয়ে বেশি গুলিয়ে যায়। সহজ করে ভাব:

Function App

এটা deployment unit — মানে Azure-এ যে resource তুমি deploy করো। এটা একটা container যেটার ভেতরে এক বা একাধিক Function থাকে। একই Function App-এর সব Function একই hosting plan, runtime version, configuration, App Settings, Managed Identity, আর deployment share করে।

Function

এটা একটা individual code unit — একটাই trigger থাকে। C#-এ একটা class যার একটা method-এ [Function("Name")] attribute লাগানো থাকে। এটা একটাই কাজ করে: একটা trigger-এ react করে, optionally binding ব্যবহার করে।

Function App Structure
Function App (Azure Resource – deployment unit)
├── App Settings / Configuration         ← সব Functions share করে
├── Managed Identity                     ← সব Functions share করে
├── Hosting Plan (Consumption/Premium)   ← সব Functions share করে
│
├── Function: ProcessOrder               ← HTTP Trigger
├── Function: SendNightlyReport          ← Timer Trigger

Interview Tip

"Function App" ≠ "Function"। Function App হলো যেটা তুমি Azure-এ deploy করো। Functions হলো তার ভেতরের individual executable unit। একই Function App-এর সব Functions configuration, secrets, আর identity share করে — এরা কিন্তু আলাদা independent application নয়।

Azure Functions কীভাবে কাজ করে — Event-Driven Model

প্রতিটা Function শুরু হয় একটা Trigger দিয়ে। Trigger হলো সেই জিনিস যেটা Function-কে চালু করে। Trigger ছাড়া Function কখনো execute হয় না।

Event ঘটে (HTTP request / Timer / Message / Blob upload)
↓
Azure Functions Runtime Trigger detect করে
↓
Worker Process allocate হয় (অথবা warm থাকলে reuse হয়)
↓

↓

↓

Serverless Computing — "Serverless" মানে কী আসলে?

Serverless মানে server নেই — এটা ভুল ধারণা। মানে হলো তুমি server manage করো না। Azure নিজেই provision করে, patch করে, scale করে, আর শুধু actual execution time-এর জন্য bill করে।

Supporting Explanation
  • No server management — Azure নিজেই OS, runtime, patching handle করে।
  • Automatic scaling — demand বাড়লে Azure scale out করে, idle থাকলে zero-তে নামিয়ে দেয় (Consumption plan)।
  • Pay-per-execution — execution count আর consumed memory/time অনুযায়ী bill হয়, uptime অনুযায়ী নয়।
  • Stateless by design — প্রতিটা function execution independent। দুটো invocation-এর মধ্যে কোনো guaranteed shared memory নেই।

Azure Functions কখন ব্যবহার করবে

  • Event-driven tasks — message process করা, file upload-এ react করা, webhook handle করা।
  • Scheduled jobs — রাতের report generation, data cleanup, token refresh।
  • Lightweight HTTP APIs — microservice endpoint, internal API।
  • Glue code / integration — এক service থেকে আরেক service-এ data পাঠানো (যেমন Event Grid event receive করে Cosmos DB-তে লেখা)।
  • Background processing — image resizing, PDF generation, queue message-এ triggered email sending।

Azure Functions কখন ব্যবহার করবে না

Warning
  • Long-running, stateful workflows — এখানে Azure Durable Functions বা Logic Apps ব্যবহার করো।
  • Always-running, latency-sensitive APIs — Consumption plan-এ cold start সমস্যা হয়। App Service বা Premium plan বিবেচনা করো।
  • CPU-intensive workloads — Functions-এর execution timeout আছে। বড় data processing batch compute-এ করো।
  • Complex session management — Functions stateless। Memory-তে user session state রেখো না।

Q2
Triggers & Bindings — What Are They and How Do They Work?

সমস্যাটা কোথায়?

Triggers আর Bindings না থাকলে প্রতিটা Function-এ infrastructure connection code লিখতে হতো — queue থেকে পড়া, Blob Storage-এ লেখা, Service Bus-এ connect করা ইত্যাদি। এতে Functions জটিল হতো আর test করা কঠিন হতো। Triggers আর Bindings এই সমস্যা সমাধান করে: কী Function চালু করবে এবং Function কোথা থেকে data পড়বে/লিখবে — এগুলো আলাদা করে দেয়।

Core Concept – Trigger

Trigger হলো সেটা যেটা Function execute করায়। প্রতিটা Function-এ exactly একটাই trigger থাকতে পারে। Trigger event data-টা তোমার function method-এর parameter হিসেবে দেয়। উদাহরণ: incoming HTTP request, queue-এ নতুন message, timer fire করা, blob upload হওয়া।

Core Concept – Binding

Binding হলো external service-এর সাথে declarative connection। নিজে connection code লিখতে হয় না। দুই ধরনের:

  • Input Binding — external source থেকে data পড়ে function-এর parameter হিসেবে দেয়।
  • Output Binding — function execute হলে external destination-এ data লেখে।

মূল নিয়মগুলো

  • প্রতিটা Function-এ exactly একটা trigger থাকে।
  • একটা Function-এ শূন্য বা একাধিক input binding থাকতে পারে।
  • একটা Function-এ শূন্য বা একাধিক output binding থাকতে পারে।
  • Trigger নিজেও data deliver করতে পারে (যেমন HTTP request body, queue message)।
Trigger + Binding Execution Model
External World
│
├── HTTP Request          ──→  [HTTP Trigger]  ──→ Function executes
├── Timer fires           ──→  [Timer Trigger] ──→ Function executes
├── Blob uploaded         ──→  [Blob Trigger]  ──→ Function executes
└── Queue message arrives ──→  [Queue Trigger] ──→ Function executes
                                                        │
                              [Input Binding]  ──→ reads from Cosmos DB / Table
                                                        │
                              [Output Binding] ──→ writes to Queue / Blob / Table

C# Example — Timer Trigger with Queue Output Binding

Functions/ReportScheduler.cs C# · .NET Isolated 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class ReportScheduler
{
    private readonly ILogger<ReportScheduler> _logger;

    public ReportScheduler(ILogger<ReportScheduler> logger)
        => _logger = logger;

    // TRIGGER: প্রতিদিন রাত ১২টায় fire করে (UTC)
    // OUTPUT BINDING: storage queue-এ message লেখে
    [Function("ReportScheduler")]
    [QueueOutput("report-jobs", Connection = "AzureWebJobsStorage")]
    public string Run(
        [TimerTrigger("0 0 0 * * *")] TimerInfo timerInfo)
    {
        _logger.LogInformation("Scheduler fired. Queuing report job.");
        // return value automatically queue-এ লেখা হয়
        return $"GenerateReport:{DateTime.UtcNow:yyyy-MM-dd}";
    }
}

লক্ষ্য কর — কোনো queue connection code নেই, কোনো QueueClient নেই। Output binding সব কিছু declaratively handle করেছে [QueueOutput] attribute দিয়ে। Return value automatically report-jobs queue-এ চলে যায়।

Think About It

Binding ব্যবহার না করে QueueServiceClient inject করে manually লিখলেও হতো। কিন্তু simple case-এ binding অনেক সহজ। Complex scenario-তে (conditional write, multiple messages, per-message error handling) সেক্ষেত্রে client inject করাই ভালো। Binding হলো "easy path" — full control-এর বিকল্প নয়।

⚡ Quick Revision — Ch01

  • Function = একটা trigger সহ individual code unit। Function App = deployment container যেটা multiple Functions ধরে।
  • একই Function App-এর সব Functions share করে: App Settings, Managed Identity, Hosting Plan, runtime version।
  • Serverless = server management নেই, pay-per-execution, auto-scale, stateless।
  • Trigger = Function চালু করে। প্রতিটা Function-এ exactly ONE trigger।
  • Input Binding = external source থেকে data পড়ে। Output Binding = external destination-এ data লেখে।
  • Bindings declarative — simple case-এ boilerplate connection code লাগে না।
  • Interview trap: "একটা Function-এ কি multiple trigger হতে পারে?" → না। শুধু ONE।
  • মনে রাখার মূল কথা: Function App হলো container; Function হলো single event-handler। Trigger চালু করে, bindings বাইরের জগতের সাথে connect করে।

Q3
HTTP Trigger — Complete Practical Implementation

সবচেয়ে বেশি ব্যবহৃত Trigger — এবং সবচেয়ে বেশি ভুল বোঝা

HTTP Trigger তোমার Function-কে একটা REST API endpoint বানিয়ে দেয়। কোনো client (browser, Postman, অন্য service) Function-এর URL-এ HTTP request পাঠালে trigger fire করে, তোমার code চলে।

Core Concept

.NET Isolated Worker model-এ HTTP Trigger HttpRequestData ব্যবহার করে (ASP.NET Core-এর HttpRequest নয়)। তুমি নিজে HttpResponseData তৈরি করো। কারণ Isolated Worker একটা আলাদা process-এ চলে — ASP.NET Core-এর HTTP types সরাসরি available নয়।

Functions/OrderFunction.csC# · .NET Isolated
public class OrderFunction
{
    private readonly IOrderService _orderService;
    private readonly ILogger<OrderFunction> _logger;
    public OrderFunction(IOrderService s, ILogger<OrderFunction> l) { _orderService=s; _logger=l; }

    // GET /api/orders/{id}
    [Function("GetOrder")]
    public async Task<HttpResponseData> GetOrder(
        [HttpTrigger(AuthorizationLevel.Function, "get", Route = "orders/{id}")] HttpRequestData req, string id)
    {
        var order = await _orderService.GetByIdAsync(id);
        if (order == null) { var r = req.CreateResponse(HttpStatusCode.NotFound); await r.WriteStringAsync("Not found"); return r; }
        var res = req.CreateResponse(HttpStatusCode.OK);
        await res.WriteAsJsonAsync(order); return res;
    }

    // POST /api/orders — body থেকে manually deserialize করতে হয়
    [Function("CreateOrder")]
    public async Task<HttpResponseData> CreateOrder(
        [HttpTrigger(AuthorizationLevel.Function, "post", Route = "orders")] HttpRequestData req)
    {
        var body = await req.ReadAsStringAsync();
        var order = JsonSerializer.Deserialize<CreateOrderRequest>(body!);
        var created = await _orderService.CreateAsync(order!);
        var res = req.CreateResponse(HttpStatusCode.Created);
        await res.WriteAsJsonAsync(created); return res;
    }
}
  • Route = "orders/{id}" — route parameter id automatically method parameter হিসেবে inject হয়।
  • req.ReadAsStringAsync() — Isolated Worker-এ body নিজে manually পড়তে হয়, কোনো automatic model binding নেই।
  • req.CreateResponse(...) দিয়ে response তৈরি করো, body/headers attach করো, return করো।
Interview Tip — Route Prefix

Default-এ সব HTTP Function-এর URL-এ /api/ prefix থাকে। Route = "orders/{id}" মানে আসল URL হলো /api/orders/{id}। এটা host.json-এ "extensions.http.routePrefix" দিয়ে বদলানো যায়।

Think About It

AuthorizationLevel.Function + Function Key কি সত্যিই "secure"? Key হলো static secret — URL বা header-এ থাকে। কেউ request capture করলে key পেয়ে যাবে। Production-এ sensitive data-র জন্য Entra ID + JWT ব্যবহার করা উচিত — token short-lived, identity-bound, আর claims থাকে।

Warning — Master Key

Master Key তোমার পুরো Function App-এ administrative access দেয় — Azure Functions Admin API দিয়ে Functions list, modify, delete করার ক্ষমতাসহ। এটা rotate করা যায় না, শুধু regenerate করা যায়। Client code-এ কখনো expose করো না, App Settings-এ store করো না, log করো না। Leak হলে Azure Portal থেকে অবিলম্বে regenerate করো।

Best Practice — প্রতিটি Caller-এর জন্য আলাদা Named Key

সবাইকে একই default key দিও না। প্রতিটি caller-এর জন্য আলাদা named key তৈরি করো (যেমন service-a-key, service-b-key)। Service A compromise হলে শুধু তার key regenerate বা delete করো — Service B-তে কোনো প্রভাব পড়বে না। এটাই Function Keys-এ least privilege principle।

// AuthorizationLevel.Anonymous রাখো — JWT নিজে validate করো
[Function("SecuredOrder")]
public async Task<HttpResponseData> Run(
    [HttpTrigger(AuthorizationLevel.Anonymous, "get")] HttpRequestData req)
{
    // 1. Authorization header থেকে Bearer token বের করো
    if (!req.Headers.TryGetValues("Authorization", out var vals))
        return req.CreateResponse(HttpStatusCode.Unauthorized);
    var token = vals.First()[7..]; // "Bearer " সরাও

    // 2. Token validate করো (audience, issuer, signature, expiry)
    var principal = await _tokenValidator.ValidateAsync(token);
    if (principal == null) return req.CreateResponse(HttpStatusCode.Unauthorized);

    // 3. Role/claim check করো
    if (!principal.IsInRole("Orders.Read")) return req.CreateResponse(HttpStatusCode.Forbidden);

    // 4. Business logic চালাও
    var res = req.CreateResponse(HttpStatusCode.OK);
    await res.WriteAsJsonAsync(new { message = "ok" }); return res;
}

Q5
Timer Trigger — Scheduled Functions

Timer Trigger কখন দরকার?

যখনই schedule-এ কিছু করতে হবে — রাতে, প্রতি ঘণ্টায়, প্রতি ৫ মিনিটে — Timer Trigger ব্যবহার করো। Azure-এর cron job বলতে পারো।

Core Concept — NCRONTAB Expression

Timer Trigger NCRONTAB format ব্যবহার করে (6 part — classic 5-part cron নয়): {second} {minute} {hour} {day} {month} {day-of-week}

  • 0 0 * * * * — প্রতি ঘণ্টার শুরুতে
  • 0 */5 * * * * — প্রতি ৫ মিনিটে
  • 0 0 0 * * * — প্রতিদিন মধ্যরাতে (UTC)
  • %TimerSchedule% — App Setting থেকে পড়ে, environment অনুযায়ী আলাদা schedule রাখা যায়
Functions/NightlyReportFunction.csC# · Timer Trigger
[Function("NightlyReport")]
public async Task Run([TimerTrigger("%NightlyReportSchedule%")] TimerInfo timerInfo)
{
    if (timerInfo.IsPastDue)
        _logger.LogWarning("Timer late fired! Missed execution.");
    _logger.LogInformation("Next run: {Next}", timerInfo.ScheduleStatus?.Next);
    await _reportService.GenerateDailySalesReportAsync();
}
Important — IsPastDue

IsPastDue true হয় যখন scheduled execution miss হয়ে যায় (যেমন Function App scale-to-zero ছিল)। এটা check করে log করা উচিত। Critical job হলে skip করার সিদ্ধান্তও নিতে পারো।

What If — Scale-Out + Timer

Function App যদি multiple instance-এ scale হয়, সব instance একসাথে timer trigger করতে চাইবে। Azure একটা blob-based distributed lock ("singleton host lease") ব্যবহার করে — শুধু একটা instance execute করে। এটা নিজে implement করতে হয় না।

.NET Isolated Worker — Complete Architecture & Project Structure

Isolated Worker Model কেন এলো?

আগে Azure Functions তোমার code host process-এর ভেতরেই চালাত (In-Process model)। সমস্যা হলো তোমার code আর Azure Functions runtime একই process শেয়ার করত — একই .NET version, একই dependencies। Azure host update করলে তোমার app ভেঙে যেতে পারত।

Core Concept — Isolated Worker

Isolated Worker Model-এ তোমার Function code একটা সম্পূর্ণ আলাদা .NET worker process-এ চলে। Azure Functions host আলাদা process, তোমার app আলাদা process — gRPC দিয়ে communicate করে। এতে তুমি পাচ্ছ:
• যেকোনো .NET version target করার স্বাধীনতা
• নিজস্ব Program.cs entry point
• Full DI container, middleware pipeline, configuration system

Middleware & Global Exception Handling

সমস্যা: প্রতিটা Function-এ try/catch

Middleware ছাড়া প্রতিটা Function-এ আলাদাভাবে try/catch লিখতে হতো। Inconsistent error handling, ভুলে গেলে বিপদ। Middleware সব invocation-এ একবার cross-cutting logic apply করে।

Middleware/ExceptionHandlingMiddleware.csC# · Isolated Worker Middleware
public class ExceptionHandlingMiddleware : IFunctionsWorkerMiddleware
{
    private readonly ILogger<ExceptionHandlingMiddleware> _logger;
    public ExceptionHandlingMiddleware(ILogger<ExceptionHandlingMiddleware> l) => _logger = l;

    public async Task Invoke(FunctionContext context, FunctionExecutionDelegate next)
    {
        try
        {
            // CorrelationId সব log-এ attach করো
            using (_logger.BeginScope(new Dictionary<string, object>
                { ["InvocationId"] = context.InvocationId }))
            {
                await next(context); // ← পরের middleware বা Function নিজেই চালাও
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled in {Fn}", context.FunctionDefinition.Name);
            // HTTP function হলে 500 response return করো
            var httpReq = await context.GetHttpRequestDataAsync();
            if (httpReq != null)
            {
                var res = httpReq.CreateResponse(HttpStatusCode.InternalServerError);
                await res.WriteAsJsonAsync(new { error = "Unexpected error.", requestId = context.InvocationId });
                context.GetInvocationResult().Value = res;
            }
        }
    }
}
  • IFunctionsWorkerMiddleware — তোমার middleware এই interface implement করবে।
  • next(context) call না করলে Function কখনো execute হবে না।
  • HTTP Function-এ context.GetHttpRequestDataAsync() দিয়ে request পাওয়া যায়, error response বানানো যায়।
  • Non-HTTP (Timer, Queue) Function-এ HTTP response নেই — শুধু log করো।
Best Practice — Middleware-এ কী রাখবে
  • Global exception handling (log + 500 return for HTTP)
  • CorrelationId generation আর propagation
  • Request/response logging
  • JWT token validation (Easy Auth না থাকলে)
  • Business logic middleware-এ রেখো না।

⚡ Quick Revision — Ch03

  • Isolated Worker = তোমার code আলাদা process-এ। Functions host আলাদা process। gRPC দিয়ে communicate।
  • Program.cs = DI + middleware। Process startup-এ একবার চলে।

Managed Identity & DefaultAzureCredential — Same Code, Local and Azure

সমস্যা: Function Azure resources-এ authenticate কীভাবে করবে?

Function-কে Blob Storage পড়তে হবে, Service Bus message পাঠাতে হবে, Key Vault থেকে secret আনতে হবে। Naive approach: connection string বা client secret App Settings-এ রাখো। সমস্যা:

Core Concept — Managed Identity

Managed Identity হলো Azure-এর দেওয়া একটা Azure AD identity যেটা তোমার Function App-এর হয়ে কাজ করে। কোনো credential কোথাও store করতে হয় না। Azure নিজেই identity lifecycle manage করে — কোনো password নেই, client secret নেই, certificate নেই।

Key Vault & Secret Management

App Settings-এ secret রাখা কেন ঠিক না?

Azure App Settings plain text environment variable হিসেবে store হয়। Contributor access আছে এমন যে কেউ দেখতে পারে। Auditing নেই, versioning নেই, rotation-এ code redeploy লাগে। Key Vault এই সব সমাধান করে।

Core Concept — Key Vault Reference

Secret value-এর বদলে App Setting-এ Key Vault reference রাখো। Format:
@Microsoft.KeyVault(SecretUri=https://my-vault.vault.azure.net/secrets/DbPassword/)
Azure runtime এটা Managed Identity দিয়ে resolve করে। তোমার code normal env var-এর মতোই পড়ে — vault URL কখনো দেখে না।

Key Vault Reference Resolution
App Setting value: @Microsoft.KeyVault(SecretUri=https://my-vault.../secrets/DbPassword/)
    │
    ▼
Azure Functions Runtime (startup বা request-এ)
    │  Function App-এর Managed Identity use করে
    ▼
Azure Key Vault
    │  Check: "Key Vault Secrets User" RBAC role আছে?
    │  হ্যাঁ → secret value return করে
    ▼
Secret value → environment variable-এ inject হয়
    │
    ▼
তোমার code: configuration["App__DbPassword"] → actual DB password
Best Practice
  • Key Vault Reference in App Settings — config value হিসেবে যা যায় (DB password, API key)। Zero code change।
  • Key Vault SDK programmatically — runtime-এ dynamically secret fetch, rotation, বা logic-based access দরকার হলে।
  • বেশিরভাগ ক্ষেত্রে Key Vault Reference-ই সহজ।
What If — Key Vault Temporarily Unavailable

Startup-এ Key Vault unreachable হলে Function App start হবে না (App Setting resolve করতে পারবে না)। Resiliency-র জন্য: Premium plan, VNet-এ Key Vault private endpoint, availability monitoring।

Q18
CORS — Why Your API Works in Postman But Fails in the Browser

সমস্যাটা কোথায়?

HTTP Function deploy করলে, Postman-এ test করলে ঠিকঠাক কাজ করে। তারপর React frontend থেকে call করলে browser CORS error দেয়। কেন?

Core Concept — Same-Origin Policy

Browser Same-Origin Policy (SOP) enforce করে: একটা webpage শুধু same origin (scheme + domain + port)-এ API call করতে পারে। https://myapp.com থেকে https://myfunctions.azurewebsites.net-এ call = cross-origin। Browser block করবে যদি না API server explicitly বলে "আমি https://myapp.com থেকে request allow করি।"
Postman browser নয় — SOP enforce করে না। এজন্যই Postman-এ কাজ করে, browser-এ করে না।

Preflight Request — সেই লুকানো OPTIONS call

Non-simple request-এর জন্য (PUT, DELETE, বা JSON Content-Type-এর POST) browser আগে একটা HTTP OPTIONS request পাঠায় — "এই real request কি করতে পারব?" Server সঠিক CORS headers দিলে তবেই real request পাঠায়।

CORS Preflight Flow
Browser (https://myapp.com)               Function App
    │                                          │
    │  OPTIONS /api/orders                     │
    │  Origin: https://myapp.com               │
    │  Access-Control-Request-Method: POST     │
    ├─────────────────────────────────────────►│
    │                                          │
    │  200 OK                                  │
    │  Access-Control-Allow-Origin: https://myapp.com
    │  Access-Control-Allow-Methods: POST, GET │
    │◄─────────────────────────────────────────┤
    │                                          │
    │  (preflight pass হয়েছে)                  │
    │  POST /api/orders  ← real request        │
    ├─────────────────────────────────────────►│
Azure CLI — CORS origins set করোAzure CLI
az functionapp cors add \
  --name my-function-app \
  --resource-group my-rg \
  --allowed-origins https://myapp.com https://staging.myapp.com
Common Mistake — Production-এ * ব্যবহার

Production-এ * (wildcard) allowed origin হিসেবে কখনো দিও না। মানে হলো যেকোনো website তোমার API call করতে পারবে — malicious site-ও। সবসময় exact origin specify করো।

Interview Tip

CORS browser enforce করে, server নয়। Server শুধু তার policy header দিয়ে জানায়। Server-to-server call (service calling another service) কখনো CORS-এর আওতায় পড়ে না।

⚡ Quick Revision — Ch06

  • CORS = browser security। শুধু browser enforce করে। Postman, curl, server-to-server: CORS নেই।
  • Same-Origin Policy: browser cross-origin request block করে যদি না API server allow করে।

  • কখনো * ব্যবহার করো না production-এ। Exact origins দাও।

Scaling, Concurrency & Cold Start

Scale-Out — আসলে কী হয়

Azure Functions শুধু "দ্রুত হয়" না — এটা আরো worker process instance যোগ করে। প্রতিটি instance স্বাধীনভাবে চলে। Scale controller trigger metrics (HTTP request queue depth, message queue depth ইত্যাদি) monitor করে এবং কখন instance add বা remove করবে তা ঠিক করে।

Scale-Out Under Load
Normal load (1 instance):
  ┌───────────────────┐
  │   Instance 1      │  ← সব request handle করে
  └───────────────────┘

Traffic spike → scale controller instances add করে:
  ┌───────────────────┐
  │   Instance 1      │
  └───────────────────┘
  ┌───────────────────┐
  │   Instance 2      │  ← নতুন instance (cold start!)
  └───────────────────┘
  ┌───────────────────┐
  │   Instance 3      │  ← নতুন instance
  └───────────────────┘

Traffic কমলে → scale in (instance সরানো হয়)

Scaling বনাম Concurrency — একটি গুরুত্বপূর্ণ পার্থক্য

Scale-Out

Worker process-এর আরো instance যোগ করা। প্রতিটি instance আলাদা compute-এ চলে। Load-এর উপর নির্ভর করে automatically হয়। মোট throughput বাড়ায়।

Concurrency

একটি instance একসাথে কতগুলো request/message process করতে পারে। HTTP-এর জন্য: Azure একই instance-এ multiple request route করতে পারে। Queue/Service Bus-এর জন্য: host.json settings দিয়ে control করা হয়।

Interview Twist — একটু ভাবো

"যদি তোমার Function App ১০টি instance-এ scale করে এবং প্রতিটি ৫টি concurrent request handle করে, কোনো risk আছে কি?"

হ্যাঁ। প্রতিটি instance-এর নিজস্ব memory ও CPU আছে। কিন্তু সবাই একই downstream dependencies share করে: তোমার database, external API, Service Bus namespace। ১০×৫ = ৫০ concurrent operation একটি database-কে overwhelm করতে পারে যেটা মাত্র ২০টি connection নেয়। Function App scale করা মানে তোমার dependencies-ও scale হয়ে যায় না।

Cold Start — কী এবং কীভাবে কমাবে

Core Concept — Cold Start

Cold start তখন হয় যখন প্রথমবার (বা idle থাকার পর) একটি নতুন worker process instance তৈরি হয়। Worker-কে করতে হয়: .NET runtime start করা, assembly load করা, Program.cs execute করা (DI registrations), তারপর request handle করা। Consumption plan-এ এটা ১-৫+ সেকেন্ড লাগতে পারে।

Cold start বাড়ানোর কারণগুলো:

  • অনেক বেশি assembly / NuGet package
  • Program.cs-এ expensive কাজ (অনেক Singleton client তৈরি)
  • Startup-এ Key Vault reference resolution
  • Isolated Worker model (in-process-এর তুলনায় সামান্য বেশি — process startup-এর কারণে)

Cold start কমানোর উপায়:

  • Premium plan: pre-warmed instances — সবসময় একটি warm instance ready থাকে
  • Program.cs-এর কাজ কমাও: যেখানে সম্ভব lazy initialization ব্যবহার করো
  • Package কম রাখো: কম assembly = দ্রুত startup
  • Flex Consumption always-ready instances: minimum instance count configure করো

Common Mistake — In-Memory State Store করা

Developers মাঝেমাঝে static dictionary বা Singleton-এর in-memory list-এ data রাখে। Locally ঠিকঠাক মনে হয়। কিন্তু production-এ:

  • ৩টি instance-এ scale → প্রতিটির নিজস্ব memory → data instances-এর মধ্যে ভাগ হয়ে/অসামঞ্জস্যপূর্ণ হয়ে যায়
  • App restart → সব in-memory data হারিয়ে যায়
  • Idle → Consumption zero-তে scale করে → সব in-memory data হারিয়ে যায়

Function App-এ কখনো critical application state memory-তে রেখো না। Azure Cache for Redis, Cosmos DB, Table Storage বা অন্য কোনো durable external store ব্যবহার করো।

⚡ Quick Revision — Ch07

  • Consumption: auto-scale, pay-per-use, cold start, ১০ মিনিট limit। Premium: pre-warmed, cold start নেই, VNet, বেশি খরচ। Dedicated: সবসময় চলে, fixed cost, full control।
  • Scale-out = বেশি instance। Concurrency = এক instance-এর মধ্যে parallel কাজ।

  • Execution timeout: Consumption = সর্বোচ্চ ১০ মিনিট। Premium/Dedicated = configurable (unlimited পর্যন্ত)।
  • Memory-তে state রেখো না — restart/scale-out-এ হারিয়ে যায়। External durable storage ব্যবহার করো।
  • Interview trap: "Function App scale করলে database-ও scale হয়" → মিথ্যা। Downstream dependency limit নিজেই সামলাতে হবে।

Function App Networking — Inbound and Outbound

Network Traffic-এর দুটো দিক

Function App networking সবসময় দুটো দিক দিয়ে ভাবো: তোমার Function-এ কী আসছে (inbound), আর তোমার Function কী পাঠাচ্ছে (outbound)।

Inbound Traffic

কে তোমার Function call করতে পারবে? Default-এ: URL (এবং সঠিক Function Key) থাকলে যে কেউ। এটা restrict করতে পারো:

  • Access Restrictions — IP allowlist/denylist rules
  • Private Endpoint — public internet access একদম নেই; শুধু VNet দিয়ে accessible
  • Function Key / Entra ID auth — identity-based restriction
Outbound Traffic

তোমার Function কীসে connect করতে পারবে? Default-এ: শুধু public internet। Private resources-এর জন্য (private database, private Service Bus, private API):

  • VNet Integration — outbound traffic একটি VNet দিয়ে route করে, private resources access করা যায়

মূল ধারণাগুলো

  • Access Restrictions: Inbound IP rules। নির্দিষ্ট IP/subnet কে Function-এর public endpoint-এ reach করতে দেওয়া বা না দেওয়া। Configure করা সহজ, API call lock down করার জন্য ভালো।
  • VNet Integration: Outbound। Function-এর outbound traffic একটি VNet-এর নির্ধারিত subnet দিয়ে যায়। Private resources call করা যায় (DB with private endpoint ইত্যাদি)।
  • Private Endpoint: Inbound। Function App-কে VNet-এর ভিতরে রাখে। Function public internet থেকে আর পৌঁছানো যায় না — শুধু VNet বা connected network থেকে।
Important — VNet Integration ≠ Private Endpoint
  • VNet Integration = outbound networking। Function private resources reach করতে পারে।
  • Private Endpoint = inbound networking। অন্যরা VNet-এর private IP দিয়ে Function reach করতে পারে।
  • সম্পূর্ণ private Function-এর জন্য দুটোই লাগে: Private Endpoint (inbound private) + VNet Integration (outbound private dependencies reach করতে)।

ILogger — Structured Logging

Azure Functions-এ Console.WriteLine ব্যবহার করো না। ILogger<T> ব্যবহার করো। এটা Application Insights-এর সাথে integrate হয়, structured log লেখে, এবং log level configuration মেনে চলে।

_logger.LogInformation($"Processing order {orderId} for customer {customerId}");

// GOOD: named parameter দিয়ে structured logging
// Application Insights OrderId ও CustomerId queryable dimension হিসেবে store করে
_logger.LogInformation(
    "Processing order. OrderId={OrderId}, CustomerId={CustomerId}",

Best Practice — Correlation ID

Important — Pipeline Variable-এ Secret রেখো না

App__ExternalApiBaseUrl-এর মতো non-sensitive App Settings pipeline variable থেকে আসতে পারে। কিন্তু secrets (passwords, connection strings) Key Vault থেকে Key Vault references হিসেবে App Settings-এ আসা উচিত — plain text pipeline secret হিসেবে inject করা উচিত নয়।

What If — Slot-Specific Settings

কিছু App Settings swap হওয়া উচিত নয় (যেমন প্রতিটি environment-এর নিজস্ব database connection string)। এগুলো portal-এ "Deployment slot setting" হিসেবে mark করো। Slot-sticky settings swap-এর সময় slot-এর সাথেই থাকে — code-এর সাথে যায় না। এতে staging code production database-এ accidentally connect হওয়া থেকে বাঁচে।

Tricky Interview Questions
Q27–Q36 — গভীর বোঝার প্রমাণ দেওয়া উত্তর
Q27
What is the difference between a Function and a Function App? What is shared by Functions inside the same Function App?

Function App = Azure resource এবং deployment unit। এক বা একাধিক Function ধারণ করার container। Function = ঠিক একটি trigger সহ individual code unit।

একই Function App-এর ভিতরের সব Function share করে: App Settings (configuration), Managed Identity, Hosting Plan (এবং এর compute), runtime version, এবং host coordination-এর জন্য ব্যবহৃত storage account। তারা আলাদা deployment pipeline share করে না — Function App deploy করলে সব Functions একসাথে deploy হয়।

Q28
Can one Azure Function have multiple triggers? Can one Function App contain Functions with different trigger types?

একটি Function-এ ঠিক একটি trigger। দুটো trigger সহ একটি Function allowed নয় — এটা Functions-এর single-responsibility model লঙ্ঘন করে।

একটি Function App-এ বিভিন্ন trigger type-এর Functions থাকতে পারে। একই Function App-এ একটি HTTP-triggered Function, একটি Timer-triggered Function, এবং একটি Service Bus-triggered Function থাকতে পারে — তারা একই hosting plan এবং configuration share করে।

Q29
What is the difference between scaling and concurrency?

Scaling = আরো worker process instance যোগ করা। Compute node multiply করে মোট capacity বাড়ায়।

Concurrency = একটি instance একসাথে কতগুলো operation handle করতে পারে। একটি instance async/await ব্যবহার করে (thread block না করে) multiple request process করতে পারে।

উদাহরণ: ৩টি instance × ১০টি concurrent request = ৩০টি total simultaneous request। কিন্তু তোমার database-কে একসাথে ৩০টি handle করতে হবে — scaling তোমার dependencies automatically scale করে না।

Q30
If a service is registered as Singleton, is that object shared across every scaled-out Function App instance?

না। Singleton মানে "প্রতি worker process-এ একটি instance"। প্রতিটি scaled-out worker process-এর নিজস্ব DI container আছে। ৫টি instance = ৫টি আলাদা Singleton object, প্রতিটি নিজের process-এ। Singleton instances-এর মধ্যে globally shared হয় না। এই কারণেই Singleton-এর in-memory cache scale-এ unreliable — আলাদা instances-এ আলাদা cache থাকে।

Q31
Why might a Function work locally but fail after deployment to Azure?

সবচেয়ে সাধারণ root causes, ঘটনার ক্রম অনুযায়ী:

  1. Configuration: App Setting Azure-এ missing বা local.settings.json-এর চেয়ে আলাদা নাম
  2. Identity / RBAC: Locally VS/CLI credential ব্যবহার হয় যার হয়তো broad access আছে। Azure-এ Managed Identity-কে প্রতিটি resource-এ explicit RBAC role assignment দরকার।
  3. Networking: Locally code সরাসরি public endpoint reach করে। Azure-এ target resource-এ Private Endpoint বা firewall থাকলে Function-এর VNet Integration দরকার।
  4. Runtime/Environment: আলাদা .NET runtime version, আলাদা OS (Windows vs Linux)
  5. Dependencies: Package না পাওয়া, publish-এর পরে DLL mismatch
Q32
Does Managed Identity work directly as your local developer identity? How does DefaultAzureCredential allow the same code to work locally and in Azure?

Managed Identity locally কাজ করে না। এটার জন্য Azure Instance Metadata Service (IMDS) দরকার, যা শুধুমাত্র Azure compute resource-এর ভিতরে থাকে।

DefaultAzureCredential multiple credential source try করে এই সমস্যা সমাধান করে। Locally এটা Visual Studio, VS Code, বা Azure CLI login খুঁজে পায় এবং সেটা ব্যবহার করে। Azure-এ এটা IMDS দিয়ে Managed Identity খুঁজে পায়। একই code — runtime-এ নীরবে আলাদা credential resolve হয়।

Q33
Is a Function Key enough to secure every production HTTP Function?

না, সব scenario-তে নয়। Function Keys static secret যা automatically expire হয় না, কোনো identity information বহন করে না, এবং compromise হলে সব callers-এ rotate করা কঠিন। এগুলো বলে না WHO call করেছে — শুধু বলে তাদের কাছে key ছিল।

Function Keys ব্যবহার করো: known internal service-এর মধ্যে simple machine-to-machine call-এর জন্য যেখানে key securely Key Vault-এ stored।

Entra ID + JWT ব্যবহার করো: user-facing API, cross-tenant scenario, claims/roles দরকার হলে, বা কে কী call করেছে তার audit trail দরকার হলে।

Q34
What happens to static variables, Singleton objects, and in-memory cache when a Function App scales out or restarts?
  • Scale-out: নতুন worker process তৈরি হয়। এটা নিজের Program.cs run করে, নিজের DI container build করে, নিজের Singleton instance তৈরি করে। Static variables এবং in-memory data নতুন instance-এ fresh (empty)। পুরনো instance নিজের data নিয়ে চলতে থাকে।
  • Restart: Worker process kill ও restart হয়। সব in-memory data — static variables, Singleton state, in-memory cache — হারিয়ে যায়।
  • উপসংহার: Critical data-এর জন্য কখনো in-memory state-এর উপর নির্ভর করো না। Redis, Cosmos DB, Table Storage, বা অন্য durable store ব্যবহার করো।
Q35
Should an Azure Function store application state in memory? What problems can occur?

না। Functions stateless হওয়ার জন্য design করা। Memory-তে state রাখলে এই সমস্যা হয়:

  • Scale-out inconsistency: Request 1 Instance 1-এর memory-তে state লেখে। Request 2 Instance 2-তে যায় — Instance 1-এর state দেখতে পায় না। Data আলাদা user-এর কাছে আলাদা বা মিলিয়ে যাচ্ছে মনে হয়।
  • Restart/scale-in-এ হারিয়ে যাওয়া: Consumption plan idle-এ zero-তে scale করে — সব in-memory data চলে যায়।
  • Sharing নেই: একই Function App-এর দুটো Function যদি same state দরকার হয়, তাদের প্রতিটির আলাদা memory — কোনো sharing নেই।
Q36
If two Functions exist inside the same Function App, are they completely independent applications? What do they share?

তারা সম্পূর্ণ independent নয়। তারা একই worker process(es)-এ চলে, একই DI container share করে, App Settings share করে, Managed Identity share করে, এবং hosting plan resources (CPU, memory) share করে।

তারা share করে না: তাদের trigger (প্রতিটির ঠিক একটি), তাদের execution context (প্রতিটি invocation independent), তাদের response (প্রতিটি নিজের request/message handle করে)।

গুরুত্বপূর্ণ implication: একটি Function-এর memory leak বা CPU-intensive loop একই Function App-এর অন্য সব Function-এর performance খারাপ করতে পারে। এজন্যই বড় Function App-গুলো domain বা criticality অনুযায়ী ভাগ করা উচিত।

Q40
External API Becomes Slow or Unavailable

Scenario: তোমার HTTP Function একটি external payment API call করে। সেই API ৩০ সেকেন্ড করে respond করছে বা timeout হচ্ছে।

এতে যে সমস্যা হয়: Function thread response-এর জন্য blocked হয়ে থাকে। Functions queued request handle করতে scale out হয়। শেষপর্যন্ত সব instance আটকে থাকে → পুরো Function App unresponsive।

সমাধান:

  • Timeout: HttpClient.Timeout set করো (যেমন ৫ সেকেন্ড)। ৩০ সেকেন্ড block না করে দ্রুত 503/Retry-After return করো।
  • Circuit Breaker (Polly): N consecutive failure-এর পরে circuit খুলে দাও এবং API না call করেই fast fail করো। Cascade failure প্রতিরোধ করে।
  • Async offloading: External API synchronously call করো না। Request accept করো, কাজ queue করো, 202 Accepted return করো। API recover হলে asynchronously process করো।
  • Retry with backoff: Transient failure-এর জন্য Polly retry with exponential backoff।

Q47
High-Traffic Function Architecture

Requirement: Unpredictable traffic spike। প্রতি মিনিটে ১০ request এবং ১,০০,০০০ request উভয়ই handle করতে হবে।

  • Premium plan: pre-warmed instances spike-এর সময় cold start দূর করে। Demand অনুযায়ী auto-scale হয়।
  • Stateless Functions: in-memory state নেই মানে যেকোনো instance যেকোনো request handle করতে পারে। পরিষ্কার horizontal scaling।
  • Heavy operation-এ Async: HTTP Function request accept করে, কাজ queue করে, 202 return করে। আলাদা worker Functions queue process করে। Ingestion থেকে processing decouple হয়।
  • Connection pooling: HttpClient Singleton হিসেবে (factory দিয়ে)। Database connection pooling। Scale-out-এ connection exhaustion প্রতিরোধ করে।
  • host.json-এ max concurrency settings: প্রতিটি instance কতগুলো message/request parallel-এ process করবে তা control করে।
  • Downstream capacity planning: database max connections, Service Bus throughput units, external API rate limits — scaled-out Function App-এর জন্য সব size করতে হবে।
