Q1
Azure Functions & Function App – Complete Fundamentals

The Problem That Gave Birth to Azure Functions

Imagine you run an e-commerce application. At 11 PM every night, you need to generate sales reports. For the other 23 hours, nothing needs to happen. With a traditional always-running Web API you pay for a VM or App Service all 24 hours — even while it's sitting idle. You also manage the OS, runtime patching, health checks, and scaling configuration yourself.

Now imagine you need to process an image every time a user uploads one to Blob Storage. You have no idea when uploads happen — could be 5 a day or 50,000 a day. You'd have to over-provision capacity just in case.

Azure Functions exist to solve exactly these two problems: pay only for what you use, and scale automatically without managing infrastructure.

Core Concept

Azure Functions is a serverless compute service. You write a small, focused piece of code (a Function). Azure takes care of the host, the runtime, the infrastructure, the scaling, and the OS. You pay only when the code actually executes.

Function vs Function App — Don't Confuse These

This is one of the most common interview mix-ups. Think of it like this:

Function App

The deployment unit. It's a container — an Azure resource that holds one or more Functions. All Functions in a Function App share the same hosting plan, runtime version, configuration, App Settings, managed identity, and deployment.

Function

An individual piece of code with one trigger. A Function is a C# class with a method decorated with [Function("Name")]. It does exactly one job: react to one trigger and optionally use bindings.

Function App Structure
Function App (Azure Resource – deployment unit)
├── App Settings / Configuration         ← shared by ALL Functions
├── Managed Identity                     ← shared by ALL Functions
├── Hosting Plan (Consumption/Premium)   ← shared by ALL Functions
│
├── Function: ProcessOrder               ← HTTP Trigger
├── Function: SendNightlyReport          ← Timer Trigger
├── Function: ProcessUploadedImage       ← Blob Trigger
└── Function: HandlePaymentEvent         ← Service Bus Trigger
Interview Tip

"Function App" ≠ "Function". A Function App is what you deploy to Azure. Functions are the individual executable units inside it. All Functions inside one Function App share configuration, secrets, and identity — they are NOT independent applications.

How Azure Functions Work — The Event-Driven Model

Every Function starts with a Trigger. A trigger is the thing that causes the Function to run. Without a trigger, a Function never executes.

Serverless Computing — What "Serverless" Really Means

Serverless does NOT mean there are no servers. It means you don't manage servers. Azure provisions them, patches them, scales them, and bills you only for actual execution time.

Supporting Explanation
  • No server management — Azure handles OS, runtime, patching.
  • Automatic scaling — Azure scales out when demand increases, scales to zero when idle (Consumption plan).
  • Pay-per-execution — Billed by number of executions and consumed memory/time, not by uptime.
  • Stateless by design — Each function execution is independent. No guaranteed shared memory between invocations.

When to Use Azure Functions

  • Event-driven tasks — process a message, react to a file upload, respond to a webhook.
  • Scheduled jobs — nightly report generation, data cleanup, token refresh.
  • Lightweight HTTP APIs — microservice endpoints, internal APIs.
  • Glue code / integration — connect one service to another (e.g., receive an Event Grid event, write to Cosmos DB).
  • Background processing — image resizing, PDF generation, email sending triggered by a queue message.

When NOT to Use Azure Functions

Warning
  • Long-running, stateful workflows — Use Azure Durable Functions or Azure Logic Apps.
  • Always-running, latency-sensitive APIs — Cold starts on Consumption plan can be a problem. Consider App Service or Premium plan.
  • CPU-intensive workloads — Functions have execution timeout limits. Large data processing is better on batch compute.
  • Complex session management — Functions are stateless. Don't store user session state in memory.

Triggers & Bindings — What Are They and How Do They Work?

Start with the Problem

Without triggers and bindings, every Function would need to contain infrastructure connection code — code to read from queues, write to Blob Storage, connect to Service Bus, etc. This would make Functions complicated and hard to test. Triggers and bindings solve this by separating what activates the Function and what data the Function reads/writes from the actual business logic.

Core Concept – Trigger

A Trigger is what causes the Function to execute. Every Function must have exactly one trigger. The trigger delivers the event data as a parameter to your function method. Examples: an incoming HTTP request, a new message on a queue, a timer firing, a blob being uploaded.

Core Concept – Binding

A Binding is a declarative connection to an external service. It removes the need to write connection code yourself. There are two kinds:

  • Input Binding — reads data from an external source and provides it as a parameter to your function.
  • Output Binding — writes data to an external destination when the function executes.

Key Rules

  • Every Function has exactly one trigger.
  • A Function can have zero or more input bindings.
  • A Function can have zero or more output bindings.
  • The trigger itself can also deliver data (e.g., the HTTP request body, the queue message).
Trigger + Binding Execution Model
External World
│
├── HTTP Request          ──→  [HTTP Trigger]  ──→ Function executes
├── Timer fires           ──→  [Timer Trigger] ──→ Function executes
├── Blob uploaded         ──→  [Blob Trigger]  ──→ Function executes
└── Queue message arrives ──→  [Queue Trigger] ──→ Function executes
                                                        │

A Simple C# Example — Timer Trigger with Queue Output Binding

Functions/ReportScheduler.cs C# · .NET Isolated 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class ReportScheduler
{
    private readonly ILogger<ReportScheduler> _logger;

    public ReportScheduler(ILogger<ReportScheduler> logger)
        => _logger = logger;

    // TRIGGER: fires every day at midnight UTC
    // OUTPUT BINDING: writes a message to a storage queue
    [Function("ReportScheduler")]
    [QueueOutput("report-jobs", Connection = "AzureWebJobsStorage")]
    public string Run(
        [TimerTrigger("0 0 0 * * *")] TimerInfo timerInfo)
    {
        _logger.LogInformation("Scheduler fired. Queuing report job.");

        // Returning a string automatically writes it to the output queue
        return $"GenerateReport:{DateTime.UtcNow:yyyy-MM-dd}";
    }
}

Notice what you did NOT write: no queue connection code, no QueueClient, no serialization to write to the queue. The output binding handled all of that declaratively via the [QueueOutput] attribute. The return value is automatically sent to the report-jobs queue.

Think About It

Why would we use a binding instead of injecting a QueueServiceClient and writing to the queue manually inside the method? Both work. But bindings are simpler for straightforward cases. For complex scenarios (conditional writes, multiple messages, error handling per message) — you'd inject the client instead. Bindings are "easy path" integration, not a replacement for full control.

⚡ Quick Revision — Ch01

  • Function = individual code unit with one trigger. Function App = the deployment container hosting multiple Functions.
  • All Functions inside one Function App share: App Settings, Managed Identity, Hosting Plan, runtime version.
  • Serverless = no server management, pay-per-execution, auto-scale, stateless.
  • Trigger = what starts the Function. Exactly ONE per Function.
  • Input Binding = reads data from external source. Output Binding = writes data to external destination.
  • Bindings are declarative. They eliminate boilerplate connection code for simple cases.
  • Interview trap: "Can a Function have multiple triggers?" → NO. One trigger only.
  • If you remember one thing: Function App is a container; Function is a single event-handler. Trigger starts it, bindings connect it to the world.

HTTP Trigger — Complete Practical Implementation

The Most Common Trigger — And the Most Misused

An HTTP Trigger turns your Function into a REST API endpoint. When a client (browser, Postman, another service) sends an HTTP request to the Function's URL, the trigger fires and your code runs. Simple idea — but the implementation details matter enormously when you move from local testing to production.

Core Concept

In .NET Isolated Worker model, HTTP Trigger uses HttpRequestData (not HttpRequest from ASP.NET Core). You create HttpResponseData manually. This is because the isolated worker runs in a separate process from the Functions host — ASP.NET Core's HTTP types aren't directly available.

Complete HTTP Function — CRUD-Style Example

Functions/OrderFunction.cs C# · .NET Isolated 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Azure.Functions.Worker.Http;
using Microsoft.Extensions.Logging;
using System.Net;
using System.Text.Json;

public class OrderFunction
{
    private readonly IOrderService _orderService;
    private readonly ILogger<OrderFunction> _logger;

    public OrderFunction(IOrderService orderService, ILogger<OrderFunction> logger)
    {
        _orderService = orderService;
        _logger = logger;
    }

    // GET /api/orders/{id}
    [Function("GetOrder")]
    public async Task<HttpResponseData> GetOrder(
        [HttpTrigger(AuthorizationLevel.Function, "get", Route = "orders/{id}")]
        HttpRequestData req,
        string id)
    {
        _logger.LogInformation("GetOrder called. OrderId={OrderId}", id);

        var order = await _orderService.GetByIdAsync(id);

        if (order == null)
        {
            var notFound = req.CreateResponse(HttpStatusCode.NotFound);
            await notFound.WriteStringAsync($"Order {id} not found.");
            return notFound;
        }

        var response = req.CreateResponse(HttpStatusCode.OK);
        await response.WriteAsJsonAsync(order);
        return response;
    }

    // POST /api/orders
    [Function("CreateOrder")]
    public async Task<HttpResponseData> CreateOrder(
        [HttpTrigger(AuthorizationLevel.Function, "post", Route = "orders")]
        HttpRequestData req)
    {
        string body = await req.ReadAsStringAsync() ?? "";
        CreateOrderRequest? orderReq;

        try
        {
            orderReq = JsonSerializer.Deserialize<CreateOrderRequest>(body);
        }
        catch
        {
            var bad = req.CreateResponse(HttpStatusCode.BadRequest);
            await bad.WriteStringAsync("Invalid JSON body.");
            return bad;
        }

        if (orderReq == null || string.IsNullOrWhiteSpace(orderReq.ProductId))
        {
            var bad = req.CreateResponse(HttpStatusCode.BadRequest);
            await bad.WriteStringAsync("ProductId is required.");
            return bad;
        }

        var created = await _orderService.CreateAsync(orderReq);
        var response = req.CreateResponse(HttpStatusCode.Created);
        response.Headers.Add("Location", $"/api/orders/{created.Id}");
        await response.WriteAsJsonAsync(created);
        return response;
    }

    // DELETE /api/orders/{id}
    [Function("DeleteOrder")]
    public async Task<HttpResponseData> DeleteOrder(
        [HttpTrigger(AuthorizationLevel.Function, "delete", Route = "orders/{id}")]
        HttpRequestData req,
        string id)
    {
        await _orderService.DeleteAsync(id);
        return req.CreateResponse(HttpStatusCode.NoContent);
    }
}

What's happening line by line:

  • [HttpTrigger(AuthorizationLevel.Function, "get", Route = "orders/{id}")] — defines the HTTP method and route. The {id} route parameter is automatically injected as the id method parameter.
  • req.ReadAsStringAsync() — reads the raw request body. In isolated worker, you always read manually; there's no model binding.
  • req.CreateResponse(HttpStatusCode.OK) — creates a response object. You attach body/headers to it and return it.
  • response.WriteAsJsonAsync(order) — serializes the object and sets Content-Type: application/json.
Interview Tip — Route Prefix

By default, all HTTP Functions have an /api/ prefix. So a Function with Route = "orders/{id}" is reachable at /api/orders/{id}. You can change or remove the prefix in host.json under "extensions.http.routePrefix".

HTTP Trigger — Authentication & Authorization

Three Levels of HTTP Function Authorization

When someone calls your Function URL, Azure can enforce access at two layers: the Function Key layer (built-in, key-based) and the identity layer (Microsoft Entra ID, JWT). These are NOT the same thing.

LevelWhat it meansWho uses it
AuthorizationLevel.AnonymousNo key required. Anyone can call.Public webhooks, health checks
AuthorizationLevel.FunctionRequires a Function-specific API key in the URL or header.Service-to-service internal APIs
AuthorizationLevel.AdminRequires the Host Master Key. Used only for admin operations.Management tooling only
Think About It

Is AuthorizationLevel.Function with a Function Key truly "secure"? The key is in the URL or a header. If someone captures the request (e.g., logs, browser history), they have the key. For APIs that handle sensitive data, identity-based auth (Entra ID + JWT) is more robust — the token is short-lived, bound to an identity, and carries claims/roles.

Adding JWT / Entra ID Authorization to an HTTP Function

Functions/SecuredOrderFunction.cs C# · Entra ID / JWT 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Azure.Functions.Worker.Http;
using Microsoft.Extensions.Logging;
using System.Net;
using System.IdentityModel.Tokens.Jwt;

public class SecuredOrderFunction
{
    private readonly ITokenValidator _tokenValidator;
    private readonly ILogger<SecuredOrderFunction> _logger;

    public SecuredOrderFunction(ITokenValidator tokenValidator, ILogger<SecuredOrderFunction> logger)
    {
        _tokenValidator = tokenValidator;
        _logger = logger;
    }

    [Function("GetSecuredOrder")]
    public async Task<HttpResponseData> Run(
        [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "secure/orders/{id}")]
        HttpRequestData req,
        string id)
    {
        // Step 1: Extract Bearer token from Authorization header
        if (!req.Headers.TryGetValues("Authorization", out var authValues))
        {
            return req.CreateResponse(HttpStatusCode.Unauthorized);
        }

        string authHeader = authValues.FirstOrDefault() ?? "";
        if (!authHeader.StartsWith("Bearer "))
        {
            return req.CreateResponse(HttpStatusCode.Unauthorized);
        }

        string token = authHeader[7..]; // strip "Bearer "

        // Step 2: Validate token (audience, issuer, signature, expiry)
        var principal = await _tokenValidator.ValidateAsync(token);
        if (principal == null)
        {
            return req.CreateResponse(HttpStatusCode.Unauthorized);
        }

        // Step 3: Check required role/claim
        if (!principal.IsInRole("Orders.Read"))
        {
            return req.CreateResponse(HttpStatusCode.Forbidden);
        }

        // Step 4: Proceed with business logic
        _logger.LogInformation("Authorized access by {User}", principal.Identity?.Name);
        var response = req.CreateResponse(HttpStatusCode.OK);
        await response.WriteAsJsonAsync(new { id, message = "Order details here" });
        return response;
    }
}
Best Practice — Production Security
  • Use AuthorizationLevel.Anonymous on the Function and validate the JWT yourself — this gives you full control over claims and roles.
  • Alternatively, enable Easy Auth (App Service Authentication) at the Function App level — Azure validates the token before your code runs.
  • For machine-to-machine internal calls: Function Keys are acceptable. For user-facing APIs or cross-tenant scenarios: always use Entra ID + JWT.

Timer Trigger — Scheduled Functions

When Do You Need a Timer Trigger?

Any time you need something to happen on a schedule — nightly, hourly, every 5 minutes — the Timer Trigger is your answer. Think of it as Azure's cron job for your application code.

Core Concept — NCRONTAB Expression

Timer Trigger uses NCRONTAB format (6 parts, not the classic 5-part cron): {second} {minute} {hour} {day} {month} {day-of-week}

  • 0 0 * * * * — every hour at minute 0
  • 0 */5 * * * * — every 5 minutes
  • 0 0 0 * * * — every day at midnight UTC
  • 0 0 9 * * 1-5 — 9 AM every weekday

You can also use a named expression: %TimerSchedule% pointing to an App Setting. This lets you configure different schedules per environment.

Functions/NightlyReportFunction.cs C# · Timer Trigger 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class NightlyReportFunction
{
    private readonly IReportService _reportService;
    private readonly ILogger<NightlyReportFunction> _logger;

    public NightlyReportFunction(IReportService reportService, ILogger<NightlyReportFunction> logger)
    {
        _reportService = reportService;
        _logger = logger;
    }

    // Schedule from App Settings: allows different schedule per environment
    [Function("NightlyReport")]
    public async Task Run(
        [TimerTrigger("%NightlyReportSchedule%")] TimerInfo timerInfo)
    {
        if (timerInfo.IsPastDue)
        {
            _logger.LogWarning("Timer fired late. Possible missed execution.");
        }

        _logger.LogInformation(
            "Nightly report started. Next run: {NextRun}",
            timerInfo.ScheduleStatus?.Next);

        await _reportService.GenerateDailySalesReportAsync();

        _logger.LogInformation("Nightly report completed.");
    }
}
Important — timerInfo.IsPastDue

IsPastDue is true when a scheduled execution was missed (e.g., the Function App was scaled to zero or restarting at the scheduled time) and the timer is firing late. Always check this and log a warning. In critical jobs, you may skip or take a different action.

What If — Timer + Scale-Out

If your Function App scales to multiple instances, all instances will try to fire the timer trigger at the same time. Azure uses a blob-based distributed lock (called "singleton host lease") to ensure only one instance executes the timer trigger at a time. You don't need to implement this yourself.

Blob Trigger — React to Storage Events

What Problem Does Blob Trigger Solve?

You have a pipeline: users upload images/documents to Azure Blob Storage, and your application needs to process them — resize, scan, extract text, etc. You don't want to poll storage every second. The Blob Trigger watches a container and fires your Function automatically when a new blob appears.

Functions/ImageProcessorFunction.cs C# · Blob Trigger 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class ImageProcessorFunction
{
    private readonly IImageService _imageService;
    private readonly ILogger<ImageProcessorFunction> _logger;

    public ImageProcessorFunction(IImageService imageService, ILogger<ImageProcessorFunction> logger)
    {
        _imageService = imageService;
        _logger = logger;
    }

    // Fires when a blob is created/updated in the "uploads" container
    // {name} is the blob file name (e.g., "photo.jpg")
    [Function("ProcessUploadedImage")]
    public async Task Run(
        [BlobTrigger("uploads/{name}", Connection = "AzureWebJobsStorage")]
        Stream blobStream,
        string name)
    {
        _logger.LogInformation("Processing blob: {BlobName}, Size: {Size}", name, blobStream.Length);

        await _imageService.ResizeAndStoreAsync(blobStream, name);

        _logger.LogInformation("Image processing complete: {BlobName}", name);
    }
}
Important — Blob Trigger Latency

The classic Blob Trigger polls storage for changes and can have up to a 10-minute delay on large containers. For production real-time processing, prefer using an Event Grid subscription on the Storage Account combined with an Event Grid Trigger on your Function — this gives near-instant reaction (sub-second latency).

Architecture Note — Managed Identity for Blob Trigger

Instead of a connection string in AzureWebJobsStorage, you can configure the Blob Trigger to use Managed Identity by setting Connection to a prefix like "MyStorage" and then in App Settings: MyStorage__blobServiceUri = https://myaccount.blob.core.windows.net and MyStorage__credential = managedidentity. This eliminates connection strings entirely.

Azure Queue Storage Trigger — Background Message Processing

The Pattern: Decouple Work from the Request

Imagine an order is placed. You don't want the HTTP endpoint to synchronously send emails, generate invoices, and update inventory — if any of those fail, the whole order fails. Instead, the HTTP endpoint places a message on a queue and returns 202 Accepted immediately. A separate Function picks up that message and does the work asynchronously.

Functions/OrderProcessorFunction.cs C# · Queue Trigger 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class OrderProcessorFunction
{
    private readonly IOrderProcessor _processor;
    private readonly ILogger<OrderProcessorFunction> _logger;

    public OrderProcessorFunction(IOrderProcessor processor, ILogger<OrderProcessorFunction> logger)
    {
        _processor = processor;
        _logger = logger;
    }

    // Fires when a message appears on the "order-events" queue
    [Function("ProcessOrderMessage")]
    public async Task Run(
        [QueueTrigger("order-events", Connection = "AzureWebJobsStorage")]
        string message)
    {
        _logger.LogInformation("Queue message received: {Message}", message);

        await _processor.ProcessAsync(message);

        // If this method completes without throwing, Azure auto-deletes the message.
        // If it throws, the message returns to the queue for retry.
        // After maxDequeueCount retries, it moves to the poison queue.
    }
}
What If — Unhandled Exception in Queue Function

If your Function throws an unhandled exception, the message is not deleted from the queue. It becomes invisible for a retry period, then reappears. After maxDequeueCount (default: 5) retries, it is moved to a poison queue named {queue-name}-poison. Always have a strategy to process or alert on poison queue messages.

Service Bus Trigger — Enterprise Messaging Integration

Service Bus vs Queue Storage — When to Use Which

Azure Queue Storage is simple and cheap. Azure Service Bus is more powerful — it supports sessions, DLQ, duplicate detection, transactions, and topics/subscriptions. In an enterprise integration scenario, you're almost always using Service Bus.

Scope Note

Here we focus only on how the Function integrates with Service Bus as a trigger. Service Bus internals (DLQ, sessions, duplicate detection, message settlement, retry) are a separate topic.

Functions/PaymentEventFunction.cs C# · Service Bus Trigger (Queue) 
using Azure.Messaging.ServiceBus;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class PaymentEventFunction
{
    private readonly ILogger<PaymentEventFunction> _logger;

    public PaymentEventFunction(ILogger<PaymentEventFunction> logger)
        => _logger = logger;

    // Queue trigger: fires when a message arrives on "payment-events" queue
    [Function("ProcessPaymentEvent")]
    public async Task Run(
        [ServiceBusTrigger("payment-events", Connection = "ServiceBusConnection")]
        ServiceBusReceivedMessage message)
    {
        _logger.LogInformation(
            "Received message. MessageId={MessageId}, Subject={Subject}",
            message.MessageId, message.Subject);

        string body = message.Body.ToString();
        _logger.LogInformation("Message body: {Body}", body);

        // Process the payment event...
        // If this completes: Azure auto-completes (acks) the message.
        // If this throws: Azure abandons the message (retries up to max delivery count).
    }
}
Functions/NotificationTopicFunction.cs C# · Service Bus Topic/Subscription Trigger 
// Topic + Subscription trigger: fires when a message arrives on a subscription
[Function("ProcessNotification")]
public async Task Run(

Instead of a connection string, use: ServiceBusConnection__fullyQualifiedNamespace = yourbus.servicebus.windows.net and ServiceBusConnection__credential = managedidentity in App Settings. Assign the Function App's Managed Identity the Azure Service Bus Data Receiver RBAC role on the namespace.

Q9
Event Grid Trigger — Event-Driven Function

What is an Event Grid Trigger Used For?

Event Grid is a routing service for events. When something happens in Azure (a blob is uploaded, a resource is deleted, a custom event is published), Event Grid can push that event to your Function in near real-time. Unlike polling, your Function sleeps until the event arrives.

Functions/BlobCreatedHandler.cs C# · Event Grid Trigger 
using Azure.Messaging;
using Azure.Messaging.EventGrid;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class BlobCreatedHandler
{
    private readonly ILogger<BlobCreatedHandler> _logger;

    public BlobCreatedHandler(ILogger<BlobCreatedHandler> logger) => _logger = logger;

    [Function("OnBlobCreated")]
    public Task Run(
        [EventGridTrigger] CloudEvent cloudEvent)
    {
        _logger.LogInformation(
            "Event received. Type={Type}, Subject={Subject}",
            cloudEvent.Type, cloudEvent.Subject);

        // cloudEvent.Data contains the event payload
        // e.g., for Microsoft.Storage.BlobCreated: blobUrl, contentType, etc.
        _logger.LogInformation("Event data: {Data}", cloudEvent.Data?.ToString());

        return Task.CompletedTask;
    }
}
Interview Tip — Event Grid vs Blob Trigger

For real-time blob processing, prefer Event Grid Trigger (subscribed to Storage Account blob events) over classic Blob Trigger. Classic Blob Trigger uses polling (up to 10-minute delay). Event Grid Trigger reacts in milliseconds. In a production pipeline processing uploaded files, this difference matters.

Q10
Event Hub Trigger — High-Volume Event Stream Processing

When is Event Hub the Right Trigger?

Event Hub is designed for massive, high-throughput event streams — IoT device telemetry, application logs, clickstream data. Azure Functions with Event Hub Trigger process these streams in batches by partition.

Functions/TelemetryFunction.cs C# · Event Hub Trigger 
using Azure.Messaging.EventHubs;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class TelemetryFunction
{
    private readonly ILogger<TelemetryFunction> _logger;

    public TelemetryFunction(ILogger<TelemetryFunction> logger) => _logger = logger;

    // Processes a BATCH of events from the event hub
    [Function("ProcessTelemetry")]
    public async Task Run(
        [EventHubTrigger("device-telemetry",
            Connection = "EventHubConnection",

.NET Isolated Worker — Complete Architecture & Project Structure

Why Does the Isolated Worker Model Exist?

Azure Functions originally ran your code inside the Functions host process (the In-Process model). This created a problem: your code and the Azure Functions runtime shared the same process, the same .NET version, and the same dependencies. If Azure updated the Functions host, your app could break. You couldn't use a newer .NET version until the host supported it.

Core Concept — Isolated Worker

In the Isolated Worker Model, your function code runs in a completely separate .NET worker process. The Azure Functions host is one process; your application is another. They communicate via gRPC. This gives you:

  • Full control over the .NET version (target any supported .NET version)
  • Your own Program.cs entry point — just like a .NET console app
  • Full DI container, middleware pipeline, configuration system
  • No dependency conflicts with the host

using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var host = new HostBuilder()
    .ConfigureFunctionsWorkerDefaults(workerApp =>
    {
        // Register middleware — applied to all function invocations
        workerApp.UseMiddleware<ExceptionHandlingMiddleware>();
    })
    .ConfigureServices((context, services) =>
    {
        // Configuration
        services.Configure<AppOptions>(context.Configuration.GetSection("App"));

        // HttpClient with typed client
        services.AddHttpClient<IExternalApiClient, ExternalApiClient>();

        // Application services
        services.AddScoped<IOrderService, OrderService>();
        services.AddScoped<IOrderRepository, OrderRepository>();
        services.AddSingleton<IReportService, ReportService>();

        // Application Insights telemetry
        services.AddApplicationInsightsTelemetryWorkerService();
        services.ConfigureFunctionsApplicationInsights();
    })
    .Build();

What happens when the worker process starts:

  • HostBuilder bootstraps the application — this is the same Microsoft.Extensions.Hosting model used in ASP.NET Core and background services.
  • ConfigureFunctionsWorkerDefaults registers the Functions-specific plumbing: the gRPC channel to the host, serialization, trigger metadata.
  • ConfigureServices is where you register all your dependencies — this runs once at startup, not on every Function invocation.
  • host.RunAsync() starts the worker and keeps it alive, listening for invocations from the Functions host.
Important — Startup vs Invocation

DI registration in Program.cs happens once at process startup. Singleton objects are created once and reused. Scoped objects are created per invocation. A cold start = worker process restarted = all objects rebuilt. But once warm, subsequent invocations reuse the same Singleton instances.

Interview Twist — Singleton + Scale-Out

"Your Function App uses a Singleton service and Azure scales the app to 5 worker instances. Do all 5 instances share exactly one Singleton object?"

No. Each worker process has its own DI container. A Singleton is "one per worker process" — not one globally across all instances. If you scale to 5 instances, there are 5 separate worker processes, each with their own Singleton instance. This is why in-memory state in a Singleton is unreliable in a scaled-out Function App.

Q14
Middleware & Global Exception Handling

The Problem: Repetitive try/catch in Every Function

Without middleware, every Function would need its own try/catch block to handle unhandled exceptions, log errors, and return proper error responses. That's repetitive, inconsistent, and easy to forget. Middleware solves this by applying cross-cutting logic once, to every invocation.

Core Concept — Middleware Pipeline

In Isolated Worker, middleware wraps around every Function invocation. It runs before and after your Function code. Common uses: global exception handling, logging request/response, adding correlation IDs, authentication validation.

Middleware/ExceptionHandlingMiddleware.cs C# · Isolated Worker Middleware 
using Microsoft.Azure.Functions.Worker;
using Microsoft.Azure.Functions.Worker.Http;
using Microsoft.Azure.Functions.Worker.Middleware;
using Microsoft.Extensions.Logging;
using System.Net;

public class ExceptionHandlingMiddleware : IFunctionsWorkerMiddleware
{
    private readonly ILogger<ExceptionHandlingMiddleware> _logger;

    public ExceptionHandlingMiddleware(ILogger<ExceptionHandlingMiddleware> logger)
        => _logger = logger;

    public async Task Invoke(FunctionContext context, FunctionExecutionDelegate next)
    {
        try
        {
            // Attach correlation ID to every invocation
            using (_logger.BeginScope(new Dictionary<string, object>
            {
                ["InvocationId"] = context.InvocationId,
                ["FunctionName"] = context.FunctionDefinition.Name
            }))
            {
                await next(context); // ← call the next middleware or the function itself
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled exception in function {FunctionName}",
                context.FunctionDefinition.Name);

            // For HTTP functions: return 500 instead of letting the host crash
            var httpReqData = await context.GetHttpRequestDataAsync();
            if (httpReqData != null)
            {
                var response = httpReqData.CreateResponse(HttpStatusCode.InternalServerError);
                await response.WriteAsJsonAsync(new
                {
                    error = "An unexpected error occurred.",
                    requestId = context.InvocationId
                });

                var invocationResult = context.GetInvocationResult();
                invocationResult.Value = response;
            }
        }
    }
}

Key points:

  • IFunctionsWorkerMiddleware — the interface your middleware must implement.
  • FunctionExecutionDelegate next — calling next(context) passes control to the next middleware or to the Function itself. If you don't call it, the Function never runs.
  • context.GetHttpRequestDataAsync() — retrieves the HTTP request if this is an HTTP-triggered function, allowing you to construct an error response.
  • For non-HTTP functions (Timer, Queue, etc.), there's no HTTP response to construct — just log the error and decide whether to rethrow.
Best Practice — What to Put in Middleware
  • Global exception handling (log + return 500 for HTTP)
  • Correlation ID generation and propagation
  • Request/response logging
  • JWT token validation (if not using Easy Auth)

Do NOT put business logic in middleware. Middleware is for cross-cutting infrastructure concerns only.

⚡ Quick Revision — Ch03

  • Isolated Worker = your code in a separate process from the Functions host. Communicate via gRPC.
  • Program.cs = DI registrations, middleware, host configuration. Runs once at startup.
  • Singleton: one per worker process (NOT globally shared across scale-out instances).
  • Scoped: one per Function invocation. Disposed after invocation completes.
  • Transient: new instance every time requested from DI.
  • Keep Functions thin — no business logic. Functions call Services; Services call Repositories.
  • Middleware wraps every invocation. Use for: global exception handling, correlation ID, JWT validation.

Q16
Managed Identity & DefaultAzureCredential — Same Code, Local and Azure

The Problem: How Does Your Function Authenticate to Azure Resources?

Your Function needs to read from Blob Storage, send a Service Bus message, and fetch a secret from Key Vault. These are all secured Azure resources. You need to authenticate. The naive approach: put a connection string or client secret in App Settings. But then:

  • The secret is visible to anyone with Portal access
  • Secrets expire and need rotation — someone has to manage that
  • If the secret leaks, attackers get full access
Core Concept — Managed Identity

Managed Identity is an Azure Active Directory identity automatically assigned to your Function App by Azure. Your Function can use this identity to authenticate to any Azure resource that supports Azure AD authentication — without storing any credentials anywhere. Azure manages the identity lifecycle: no passwords, no client secrets, no certificates to rotate.

Managed Identity Authentication Flow
Function App (with System-assigned Managed Identity)
    │
    │  1. "I need a token for Blob Storage"
    ▼
Azure Instance Metadata Service (IMDS)  ← built into every Azure VM/worker
    │
    │  2. Returns short-lived access token (valid ~1 hour, auto-renewed)
    ▼
Function Code receives token
    │
    │  3. Uses token in API call to Blob Storage
    ▼
Azure Blob Storage
    │
    │  4. Validates token via Azure AD
    │     - Is this a valid identity?
    │     - Does it have the required RBAC role on this resource?
    ▼
Access granted (or denied)

TypeLifecycleSharingWhen to use

Here's the magic that makes the same C# code work both locally and in Azure. DefaultAzureCredential tries multiple credential sources in order:

Q17
Key Vault & Secret Management

Why Can't I Just Put Secrets in App Settings?

App Settings in Azure are stored as plain text environment variables. Anyone with Contributor or higher access to the Function App can see them. They aren't audited, versioned, or rotatable without a code deploy. Key Vault solves all of this.

Core Concept — Key Vault Reference

Instead of putting a secret value in an App Setting, you put a Key Vault reference. The format is:

@Microsoft.KeyVault(SecretUri=https://my-vault.vault.azure.net/secrets/DbPassword/)

Azure resolves this reference at runtime using the Function App's Managed Identity. Your code reads it as a normal environment variable — it never sees the vault URL.

Key Vault Reference Resolution Flow
App Setting value: @Microsoft.KeyVault(SecretUri=https://my-vault.vault.azure.net/secrets/DbPassword/)
    │
    ▼
Azure Functions Runtime (at startup or per-request)
    │
    │  Uses Function App's Managed Identity
    ▼
Azure Key Vault
    │
    │  Checks: Does this Managed Identity have "Key Vault Secrets User" role?
    │  If yes: returns secret value
    ▼
Secret value injected into environment variable
    │
    ▼
Your code reads: configuration["App__DbPassword"] → actual DB password

Programmatic Key Vault Access (when you need more control)

Services/SecretService.cs C# · Azure Key Vault SDK 
using Azure.Identity;
using Azure.Security.KeyVault.Secrets;

public class SecretService
{
    private readonly SecretClient _secretClient;

    public SecretService(IOptions<AppOptions> options)
    {
        // DefaultAzureCredential: uses VS/CLI locally, Managed Identity in Azure
        _secretClient = new SecretClient(
            new Uri(options.Value.KeyVaultUri),
            new DefaultAzureCredential());
    }

    public async Task<string> GetSecretAsync(string secretName)
    {
        KeyVaultSecret secret = await _secretClient.GetSecretAsync(secretName);
        return secret.Value;
    }
}
Best Practice — Key Vault Reference vs SDK
  • Key Vault Reference in App Settings — best for secrets that map to configuration values (DB passwords, API keys). Zero code change needed. Resolved automatically.
  • Key Vault SDK programmatically — best when you need to fetch secrets dynamically at runtime, rotate them, or fetch different secrets based on logic.

For most cases, Key Vault References (App Setting references) are simpler and preferred.

What If — Key Vault Is Temporarily Unavailable

If Key Vault is unreachable at startup (network issue, outage), your Function App will fail to start because it can't resolve the App Setting references. For resiliency: use a Premium plan (always warm, VNet connectivity), configure Key Vault with private endpoint so it's accessible via VNet, and set up proper retry/availability monitoring for Key Vault.

  • Managed Identity = Azure-managed identity for your Function App. No passwords to store.
  • System-assigned: tied to the app, deleted with it. User-assigned: independent, reusable across apps.
  • DefaultAzureCredential = tries multiple auth strategies in order. Uses VS/CLI locally, Managed Identity in Azure. Same code works everywhere.
  • Managed Identity alone does NOT grant access. Must assign RBAC roles on target resources.
  • Key Vault Reference = put @Microsoft.KeyVault(...) as App Setting value. Azure resolves it using Managed Identity. Your code reads it as a normal env var.
  • Interview trap: "Does Managed Identity work locally?" → No, it needs IMDS (only in Azure). Locally, DefaultAzureCredential falls back to VS/CLI credential.
  • If you remember one thing: No secrets in code or App Settings. Managed Identity + RBAC + Key Vault = secretless production architecture.

Q18
CORS — Why Your API Works in Postman But Fails in the Browser

The Problem

You deploy an HTTP Function. You test it in Postman — works perfectly. You build a React frontend at https://myapp.com that calls your Function at https://myfunctions.azurewebsites.net/api/orders. The browser refuses the request with a CORS error. Why?

Core Concept — Same-Origin Policy

Browsers enforce the Same-Origin Policy (SOP): a webpage can only make API calls to the same origin (scheme + domain + port). When your frontend at https://myapp.com calls https://myfunctions.azurewebsites.net — that's a cross-origin request. The browser blocks it unless the API server explicitly says "I allow requests from https://myapp.com."

Postman is NOT a browser. It doesn't enforce SOP. That's why Postman works and the browser doesn't.

The Preflight Request — The OPTIONS Request You Never Sent

For non-simple requests (PUT, DELETE, or POST with JSON content-type), the browser first sends an HTTP OPTIONS request (the "preflight") asking "can I make this real request?" If the server doesn't respond with the right CORS headers, the browser blocks the real request.

        │  OPTIONS /api/orders HTTP/1.1                │
        │  Origin: https://myapp.com                   │
        │  Access-Control-Request-Method: POST         │
        │  Access-Control-Request-Headers: Content-Type│
        ├─────────────────────────────────────────────►│
        │                                              │
        │  HTTP 200 OK                                 │
        │  Access-Control-Allow-Origin: https://myapp.com
        │  Access-Control-Allow-Methods: POST, GET     │
        │  Access-Control-Allow-Headers: Content-Type  │

        │  POST /api/orders                            │
        ├─────────────────────────────────────────────►│

There are two ways to configure CORS for Azure Functions:

1. Azure Portal / App Configuration (Recommended for production)

In the Azure Portal → your Function App → API → CORS. Add your allowed origins. Azure handles the preflight responses automatically.

  --name my-function-app \
  --resource-group my-rg \
  --allowed-origins https://myapp.com https://staging.myapp.com

2. In Code (host.json)

  "extensions": {
    "http": {
      "routePrefix": "api"
    }

    "CORS": "http://localhost:3000",
    "CORSCredentials": true
  }
}
Common Mistake — Using * in Production

Never use * (wildcard) as the allowed origin in production. It means any website can call your API — including malicious ones. Always specify exact origins. For APIs that serve authenticated users, also never use * with AllowCredentials: true — browsers reject this combination entirely.

Interview Tip

CORS is enforced by the browser, not the server. The server just communicates its policy via headers. Server-to-server calls (service calling another service) are never affected by CORS. A load balancer, API Gateway, or another microservice calling your Function is NOT a CORS scenario.

⚡ Quick Revision — Ch06

  • CORS = browser security enforcement. Only browsers enforce it. Postman, curl, server-to-server: no CORS.
  • Same-Origin Policy: browser blocks cross-origin requests unless the API server allows them via CORS headers.
  • Preflight: browser sends OPTIONS request first for non-simple requests. Server must respond with allowed origins/methods/headers.
  • Configure CORS in Azure Portal (API → CORS) or Azure CLI. Not in host.json for deployed functions.
  • Never use * in production for public APIs — specify exact origins.
  • Interview trap: "CORS is a server security feature" → Partially wrong. It's enforced by the browser. The server sets the policy; the browser enforces it.

Q20
Scaling, Concurrency & Cold Start

Scale-Out — What Actually Happens

Azure Functions doesn't just "become faster" under load. It adds more worker process instances. Each instance runs independently. The scale controller monitors trigger metrics (HTTP request queue depth, message queue depth, etc.) and decides when to add or remove instances.

Scale-Out Under Load
Normal load (1 instance):
  ┌───────────────────┐
  │   Instance 1      │  ← handles all requests
  └───────────────────┘

Traffic spike → scale controller adds instances:
  ┌───────────────────┐
  │   Instance 1      │
  └───────────────────┘
  ┌───────────────────┐
  │   Instance 2      │  ← new instance (cold start!)
  └───────────────────┘
  ┌───────────────────┐
  │   Instance 3      │  ← new instance
  └───────────────────┘

Traffic drops → scale in (instances removed)

Scaling vs Concurrency — A Critical Distinction

Scale-Out

Adding more instances of the worker process. Each instance runs on separate compute. Happens automatically based on load. Increases total throughput.

Concurrency

How many requests/messages a single instance can process simultaneously. For HTTP: Azure can route multiple requests to the same instance. For Queue/Service Bus: controlled by host.json settings.

Interview Twist

"If your Function App scales to 10 instances and each handles 5 concurrent requests, is there a risk?"

Yes. Each instance has its own memory and CPU. But they all share the same downstream dependencies: your database, your external API, your Service Bus namespace. Scaling to 10×5 = 50 concurrent operations can overwhelm a database that only accepts 20 connections. Scaling the Function App is not the same as scaling your dependencies.

Cold Start — What It Is and How to Reduce It

Core Concept — Cold Start

A cold start happens when a new worker process instance is created for the first time (or after being idle). The worker must: start the .NET runtime, load your assemblies, execute Program.cs (DI registrations), and then handle your request. This can take 1-5+ seconds on Consumption plan.

Factors that increase cold start time:

  • Large number of assemblies / NuGet packages
  • Expensive operations in Program.cs (creating many Singleton clients)
  • Key Vault reference resolution at startup
  • Isolated Worker model (slightly higher than in-process due to process startup)

How to reduce cold starts:

  • Premium plan: pre-warmed instances — there's always at least one warm instance waiting
  • Minimize Program.cs work: lazy initialization where possible
  • Keep packages lean: fewer assemblies = faster startup
  • Flex Consumption always-ready instances: configure a minimum instance count

Function App Networking — Inbound and Outbound

The Two Directions of Network Traffic

Always think about Function App networking in two directions: what comes into your Function (inbound), and what your Function sends out (outbound).

Inbound Traffic

Who can call your Function? By default: anyone with the URL (and the right Function Key). You can restrict this with:

  • Access Restrictions — IP allowlist/denylist rules
  • Private Endpoint — no public internet access at all; only accessible via VNet
  • Function Key / Entra ID auth — identity-based restriction
Outbound Traffic

What can your Function connect to? By default: public internet only. For private resources (private databases, private Service Bus, private APIs):

  • VNet Integration — routes outbound traffic through a VNet, allowing access to private resources

Key Concepts

  • Access Restrictions: Inbound IP rules. Allow only specific IPs/subnets to reach your Function's public endpoint. Easy to configure, good for locking down who can call the API.
  • VNet Integration: Outbound. Your Function's outbound traffic flows through a designated subnet in a VNet. Allows calling private resources (DB with private endpoint, etc.).
  • Private Endpoint: Inbound. Puts your Function App inside a VNet. The Function is no longer reachable from the public internet — only from within the VNet or connected networks.
Important — VNet Integration ≠ Private Endpoint
  • VNet Integration = outbound networking. Your Function can reach private resources.
  • Private Endpoint = inbound networking. Others reach your Function via a private IP in the VNet.
  • A truly private Function needs both: Private Endpoint (so inbound is private) + VNet Integration (so outbound reaches private dependencies).

ILogger — Structured Logging

Don't use Console.WriteLine in Azure Functions. Use ILogger<T>. It integrates with Application Insights, writes structured logs, and respects log level configuration.

_logger.LogInformation($"Processing order {orderId} for customer {customerId}");

_logger.LogInformation(
    "Processing order. OrderId={OrderId}, CustomerId={CustomerId}",

_logger.LogDebug("Detailed trace, only for dev debugging");

_logger.LogWarning("Something unexpected but recoverable");
_logger.LogError(ex, "Operation failed. OrderId={OrderId}", orderId);

Tricky Interview Questions
Q27–Q36 — Answers That Reveal Deep Understanding
Q27
What is the difference between a Function and a Function App? What is shared by Functions inside the same Function App?

Function App = the Azure resource and deployment unit. A container hosting one or more Functions. Function = individual code unit with exactly one trigger.

All Functions inside one Function App share: App Settings (configuration), Managed Identity, Hosting Plan (and its compute), runtime version, and the storage account used for host coordination. They do NOT share separate deployment pipelines — deploying the Function App deploys all Functions together.

Q28
Can one Azure Function have multiple triggers? Can one Function App contain Functions with different trigger types?

One Function = exactly one trigger. A Function with two triggers is not allowed — it violates the single-responsibility model of Functions.

One Function App CAN contain Functions with different trigger types. You can have an HTTP-triggered Function, a Timer-triggered Function, and a Service Bus-triggered Function all inside the same Function App — they share the same hosting plan and configuration.

Q29
What is the difference between scaling and concurrency?

Scaling = adding more worker process instances. Increases total capacity by multiplying compute nodes.

Concurrency = how many operations a single instance handles simultaneously. An instance can process multiple requests concurrently using async/await (not blocking threads).

Example: 3 instances × 10 concurrent requests = 30 total simultaneous requests. But your database must handle all 30 at once — scaling doesn't scale your dependencies automatically.

Q30
If a service is registered as Singleton, is that object shared across every scaled-out Function App instance?

No. A Singleton is "one instance per worker process." Each scaled-out worker process has its own DI container. 5 instances = 5 separate Singleton objects, each in their own process. Singletons are NOT globally shared across instances. This is why in-memory caches in a Singleton are unreliable at scale — different instances have different caches.

Q31
Why might a Function work locally but fail after deployment to Azure?

The most common root causes, in order of frequency:

  1. Configuration: App Setting missing or has different name in Azure vs local.settings.json
  2. Identity / RBAC: Locally uses VS/CLI credentials which may have broad access. In Azure, Managed Identity needs explicit RBAC role assignments on each resource.
  3. Networking: Locally, code reaches public endpoints directly. In Azure, if the target resource has a Private Endpoint or firewall, the Function needs VNet Integration.
  4. Runtime/Environment: Different .NET runtime version, different OS (Windows vs Linux)
  5. Dependencies: Package not found, DLL mismatch after publish
Q32
Does Managed Identity work directly as your local developer identity? How does DefaultAzureCredential allow the same code to work locally and in Azure?

Managed Identity does NOT work locally. It requires the Azure Instance Metadata Service (IMDS), which only exists inside Azure compute resources.

DefaultAzureCredential solves this by trying multiple credential sources. Locally, it finds your Visual Studio, VS Code, or Azure CLI login and uses that. In Azure, it finds the Managed Identity via IMDS. Same code — different credential resolved silently at runtime.

Q33
Is a Function Key enough to secure every production HTTP Function?

No, not for all scenarios. Function Keys are static secrets that don't expire automatically, carry no identity information, and if compromised are hard to rotate across all callers. They don't tell you WHO made the call — only that they had the key.

Use Function Keys for: simple machine-to-machine calls between known internal services where the key is stored securely in Key Vault.

Use Entra ID + JWT for: user-facing APIs, cross-tenant scenarios, APIs where you need claims/roles, or where you need audit trails of who called what.

Q34
What happens to static variables, Singleton objects, and in-memory cache when a Function App scales out or restarts?
  • Scale-out: A new worker process is created. It runs its own Program.cs, builds its own DI container, creates its own Singleton instances. Static variables and in-memory data are fresh (empty) in the new instance. The old instance continues running with its own data.
  • Restart: The worker process is killed and restarted. All in-memory data — static variables, Singleton state, in-memory cache — is lost.
  • Conclusion: Never rely on in-memory state for critical data. Use Redis, Cosmos DB, Table Storage, or another durable store.
Q35
Should an Azure Function store application state in memory? What problems can occur?

No. Functions are designed to be stateless. Storing state in memory creates these problems:

  • Scale-out inconsistency: Request 1 writes state to Instance 1's memory. Request 2 goes to Instance 2 — it doesn't see Instance 1's state. Data appears to disappear or be different for different users.
  • Loss on restart/scale-in: Consumption plan scales to zero on idle — all in-memory data is gone.
  • No sharing: If two Functions inside the same Function App need the same state, they each have their own memory — no sharing.
Q36
If two Functions exist inside the same Function App, are they completely independent applications? What do they share?

They are NOT completely independent. They run in the same worker process(es), share the same DI container, share App Settings, share Managed Identity, and share the hosting plan resources (CPU, memory).

What they DON'T share: their trigger (each has exactly one), their execution context (each invocation is independent), their response (each handles its own request/message).

Important implication: A memory leak or CPU-intensive loop in one Function can degrade performance for all other Functions in the same Function App. This is why large Function Apps should be split by domain or criticality.

Problems this creates: Function threads are blocked waiting for the response. Functions scale out to handle queued requests. Eventually all instances are stuck waiting → entire Function App becomes unresponsive.

Solutions:

  • Timeouts: Set a HttpClient.Timeout (e.g., 5 seconds). Return 503/Retry-After quickly instead of blocking for 30s.
  • Circuit Breaker (Polly): After N consecutive failures, open the circuit and fail fast without calling the API at all. Prevents cascade failures.
  • Async offloading: Don't call the external API synchronously. Accept the request, queue the work, return 202 Accepted. Process asynchronously when the API recovers.
  • Retry with backoff: Polly retry with exponential backoff for transient failures.
